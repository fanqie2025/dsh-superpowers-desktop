# 系统化排障（systematic-debugging）

排障失败多半不是不够聪明，而是顺序错了：猜一个改法、现象变了、再猜一个，最后连原本的现象都说不清。本文给的是顺序和门禁——先把现象钉住，再把根因钉住，最后才动代码。

## 何时用 / 何时不用

任何技术故障：报错、测试失败、构建失败、性能退化、集成不通、行为不符预期。

**越急越要用**：时间压力、「只差一个小改动」、已经改了几处还没好、自己没看懂现象——正是瞎猜高发区，系统性排查比反复试错快。已能指着 `文件路径:行号` 说清因果链且只改一处时，可以不走本文，但仍要留痕。

## 核心原则

1. **没复现就不要改代码。** 现象触发不稳，任何改动都无法被证伪。
2. **一次只改一个变量。** 同时改两处，现象变了也无法归因。
3. **先想清为什么改，再想清改完怎么证明没引入新问题。** 说得出「因为 X 导致 Y，所以改 X」和「改完用什么命令证明别的没坏」，说不出就退回上一步。
4. **证据要求（硬性）**：结论必须挂 `文件路径:行号`（用 `read`/`grep` 取）或命令的原始输出。「我觉得」「应该是」「大概」不算依据，转述也不算原始输出；拿不到就直说拿不到。

## 流程（四阶段，顺序不可跳）

### 阶段 1：稳定复现

- 用 `read` 看完堆栈与 warning，记下文件、行号、错误码；跳过 warning 是最常见的自伤。
- 压到最小复现，写下固定命令串与完整输出；输出长时用 `pwsh` 的 `run_in_background` 跑、`job_output` 取回。
- **判据**：同一命令连跑两次现象一致才算复现；间歇性故障只记录频率与前置条件，不得进入阶段 2。
- 查最近变更（有 git 看 diff，无 git 就按修改时间排序）。复现不出来就继续采集数据，不要猜。

### 阶段 2：定位根因

- 多组件系统先在每层边界打点（进什么／出什么、配置与环境变量），先确定**坏在哪一层**，再钻进那层读代码。
- 数据流回溯：从出错点往上游追，每步问「这个坏值是谁传进来的」，追到第一个不该是它的地方——**修在源头，不修在症状处**，并记下每环的行号。
- 找同类正常路径做参照，逐条列差异，小到「这不可能有影响」也要列。
- **判据**：能用一句「因为 X，所以 Y」讲清因果链，且每环都有 `文件路径:行号` 或命令输出支撑。

### 阶段 3：可证伪的假设与验证

- 写下假设和证伪条件：「根因是 X，证据 E；若成立，改掉 X 后 Z 会由失败变成功，而 W 不变」。没有证伪条件的假设等于没写。
- 只动一个变量做最小验证（打印一个值、关一个开关、直连一次），不顺手重构、不叠加第二个修复。
- **判据**：成立 → 进阶段 4；不成立 → 丢弃它，用新证据形成**新**假设，不在原改动上继续加。
- 已试 3 次仍不成立就质疑思路：每次修复都在别处冒新问题、或要大改才能修，那是架构不对。用 `ask_user_question` 交用户定方向，不要再试第 4 次。

### 阶段 4：修复与回归保护

- 写清「为什么改这里」，对应阶段 2 的因果链；用 `grep` 找全调用方：改的是根因还是症状？会不会伤到别的调用方？
- 先有能失败的复现：有测试框架就写测试，没有就写一次性脚本或固定命令；判据是修前失败、修后通过，两次输出都留。
- 只做一处修改，用同一复现复验，并跑相关测试或相关路径，证明**没有引入新问题**。
- 加回归保护：把复现固化成测试、脚本或写进文档的命令，说明防住哪种回归。无测试套件时退化为固定复现命令，判据不变。

## 反模式（出现即停，回阶段 1）

- 「先快速改一版，回头再查」——第一次改动就定下瞎猜基调。
- 一次改多处、顺手重构美化，然后一起跑。
- 跳过复现直接改代码，拿「手动点一下看起来好了」当验证。
- 「我觉得应该是 X」而拿不出 `文件路径:行号` 或命令输出。
- 假设不成立却在原改动上叠加第二个修复；「再试最后一次」。
- 每修一处就在别处冒出新问题，仍然接着修。

## 完成判据

逐条给证据，缺一条不许宣布修好：

1. 稳定复现的命令与原始输出已给出，连跑两次现象一致。
2. 根因结论带 `文件路径:行号` 或命令输出，能复述「因为 X 所以 Y」。
3. 本次只改一处，无关改动已剔除或单独说明。
4. 同一复现有修前失败、修后通过两次输出。
5. 相关路径/测试已跑并附输出，未覆盖部分与风险写明。
6. 回归保护已落地，说得出它防住什么。

## 与其它技能的关系

本技能是**通用骨架**；本机有更专门的技能时优先加载它们，本技能只管流程纪律：

- DNS 改写、域名解析到固定 IP → `adguard-dns-rewrite-outage-triage`
- 本机或局域网端口拿到伪造 502、401 → `localhost-curl-trap`
- 容器启动即崩、报缺依赖 → `docker-missing-deps-patch`
- 工作区读写被沙箱拒绝、ACL 异常 → `diagnose-windows-sandbox-acl`
- 采集器静默返回 0 条 → `web-scraper-selector-url-triage`
- 本地 Web 应用行为验证与截图取证 → `webapp-testing`

本机若装了 `test-driven-development`，写失败复现时加载它；宣布完成前可用 `verification-before-completion`；排查跨多轮时用 `create_goal` 钉住目标。上游同目录的 `root-cause-tracing.md`、`defense-in-depth.md`、`condition-based-waiting.md`、`find-polluter.sh` 未随本技能分发（已登记为省略），要点已内联：回溯到源头再修、修完根因可在多层补校验、用条件轮询代替固定超时。

## 本机适配注意

**环境型故障的排查顺序**：本机大量「代码 bug」其实是环境造成的。逐层证伪，哪层坐实就把根因锁在那层，不要跳过去读代码：

1. **权限/沙箱层**：策略拒绝会打印 `[sandbox: file access denied under <mode> mode]`；换写法重试没有意义——把产物落回工作区，或请用户放行。
2. **代理层**：`http_proxy`／`HTTPS_PROXY` 会劫持请求，访问 `127.0.0.1`／`192.168.x.x`／`*.local` 可能拿到**伪造**的 `502 upstream connect failed`、401 或畸形响应。加 `--noproxy '*'`（PowerShell 用 `-NoProxy`）重跑做对照，正常了 → 根因在代理，不在服务。
3. **解析层**：域名是否被 DNS 改写钉到失效 IP？用可用 IP 直连对照（见 `adguard-dns-rewrite-outage-triage`）。
4. **编码/路径层**：中文路径、CRLF、BOM——把输入复制到纯 ASCII 临时路径复跑对照。
5. 1–4 都排除后，才把根因假定在**代码层**。

**两个已知陷阱**：

- `pwsh` 在 `workspace-write` 下返回 `0xC0000142` 且零 stdout，是环境层故障而非命令写错，**不要反复重试同一条命令**（换命令、换目录、走后台都一样）。改用 `read`／`write`／`edit`／`glob`／`grep` 继续推进，确需执行程序再请用户放行。
- 访问本机与局域网服务一律加 `--noproxy`，否则会把「服务正常」误判成「服务挂了」。
