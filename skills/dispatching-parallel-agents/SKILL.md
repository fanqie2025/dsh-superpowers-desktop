# 并行子智能体派发

多个**互不相关**的问题（不同文件、不同子系统、不同失败原因）串行排查是纯浪费：每一个都能独立
推进，而且都能在不污染你上下文的前提下推进。核心原则：**一个独立问题域派一个子智能体，让它们
并发跑**。你自己的上下文留给协调与汇总，而不是被三份无关的排查日志填满。

## 何时用 / 何时不用

**用**：3 个以上失败但根因各不相同；多个子系统各自坏掉；每个问题不需要别人的结论就能理解；
彼此没有共享状态。

**不用**：失败彼此相关（修好一个可能顺带修好另一个）——先合起来查；需要系统整体状态才能判断；
子智能体会改同一批文件或抢同一份资源；还是探索阶段，你根本不知道坏在哪。

**判据（不满足就别并行）**：两个子任务的产出物集合不相交，且任何一个都不读取另一个的产物。
只要有一处共享可变状态或一条顺序依赖，并行就只会制造冲突和返工。

## 核心原则

- **并行不是免费的。** 写清晰提示词、定义边界、汇总结果、交叉验证、处理冲突都要花时间与 token。
  只有当「省下的串行时间 + 你被省下的上下文」明显超过这些开销时才值得。任务切不干净时，
  老老实实串行或自己做完更快。
- **上下文要显式构造。** `subagent` 不共享本会话；`subagent_fork` 继承本会话**已完成轮次**
  （看不到当前这轮）。两者都不要指望对方「知道背景」，缺的上下文一律写进提示词。
- **子智能体自述不是证据。** 汇总阶段必须抽查产物（文件真的写了吗、命令真的跑过吗）。

## 规模判据：用哪个工具

| 规模 | 手段 |
| --- | --- |
| 1 个任务 | 不派发，自己做 |
| 2–3 个独立域 | 同一响应里发 2–3 个 `subagent`（或 `subagent_fork`） |
| 4–10 个独立域 | 同一响应里全部发出，用 `list_agents` 统一跟踪 |
| 几十个以上独立单元，需要分阶段、结构化结果、逐项校验 | 升级到 `workflow`，写 JS 编排脚本 |

- `subagent`：全新上下文，适合自包含的独立任务；`subagent_fork`：继承本会话已完成轮次，
  适合「接着刚才的结论往下做」。**两者都默认后台运行**，返回 agent id，完成后会通知你，
  不需要空转轮询。
- 跟进用 `send_message`，中断用 `interrupt_agent`，查看状态用 `list_agents`。
- 只有真正的大规模扇出（几十上百个独立单元、要分阶段且要结构化结果）才值得上 `workflow`。
  为了两三个任务写 JS 编排脚本，是拿工具复杂度换一点点并行度，不划算。

## 流程

1. **切分独立域**：按「坏在哪」分组（例如 文件A／文件B／子系统C），逐个过一遍上面的判据，
   确认产出物不相交、无顺序依赖。写下一张域清单。判据：清单里任意两项都无法互相解锁。
2. **为每域写自包含提示词**。每条必须包含：具体范围（一个文件或一个子系统）、明确目标、
   约束（不许改哪些东西）、期望交付物，以及最重要的——**明确的验收判据**
   （跑什么、看到什么算过）。判据：把提示词单独交给一个不知情的智能体，它也能开工。
3. **同一响应里并发发出**。一条消息里发多个 `subagent` 调用即并发；一次只发一个就是串行，
   并行度白扔。判据：本响应中的派发调用数 == 域清单条数。
4. **汇总与整合**：
   - 每个返回结果都要读，但**只信产物不信自述**：文件是否真的被改（`read`）、
     声称跑过的命令是否有真实输出。
   - 检查冲突：`grep` 出各智能体声称改过的位置，看有没有改到同一处。
   - 全部回来后，由你自己跑一次完整验证（测试套件／构建／端到端命令），
     确认各修复能共存。子智能体各自「通过」不等于合起来通过。
5. **收尾**：把结果与证据写回给你自己或用户；有未决冲突就再发一个 `subagent` 专攻冲突，
   不要自己边猜边合。

## 反模式（会怎么错）

- **范围太宽**：「把所有测试修好」——子智能体立刻迷路。要「修 X 文件的 3 个失败用例」。
- **不给上下文**：「修一下竞态」——它不知道在哪。贴上报错原文、失败用例名、相关文件路径。
- **不给约束**：它可能顺手大重构。写清「不许改生产代码」或「只动测试」。
- **交付物含糊**：「修好它」——你不知道它改了什么。要「返回根因 + 改动清单 + 验证输出」。
- **盲信自述**：只看「已完成」就宣布结束——上游明确点名这是系统性错误来源。
- **共享状态硬并行**：两个智能体改同一文件、或依赖彼此结论仍强行并发，必然冲突。
- **忽略成本**：为 2 个小改动派 2 个智能体，写提示词和核对产物比自己做还慢。

## 完成判据

- 派出的每个 agent 都已返回（`list_agents` 无 running），或已被显式 `interrupt_agent`。
- 汇总表里每一行都有**你亲自验证过**的产物证据（有文件路径、有命令输出、有行号），
  而不是转述的自述。
- 任何被多个智能体触碰的文件都已消解冲突，且你能指出最终状态。
- 完整验证命令由你自己跑过一遍并通过。跑不通就走第 5 步，不要把「各自通过」当完成。
- 未解决项已明说；不许用「基本完成」收尾。

## 与其它技能的关系

- `subagent-driven-development`：把单个任务的开发循环交给子智能体；本技能管的是**多个独立任务
  之间**的并发编排，两者可叠加。
- `brainstorming` → `writing-plans`：切分与判据应先由计划确定，再谈派发。
- `using-git-worktrees`：当各域会改同一代码库且需要物理隔离时的备选手段。
- `verification-before-completion`：汇总阶段的抽查纪律与它同源，收尾前值得加载。

## 本机适配注意

- 子智能体同样受 `workspace-write` 沙箱约束：**只有会话工作区可写**，工作区外路径会被拒绝。
  不要假设它们能顺利跑 `pwsh`（该策略下 `pwsh` 有已知故障，可能返回 `0xC0000142` 且无输出）。
- 让子智能体优先用 `read`／`write`／`edit`／`glob`／`grep` 交付；确需执行程序时，在提示词里
  说明「失败就报告，不要反复重试同一条命令」，并让它们把原始报错带回来。
- 子智能体不得请求沙箱放行（无人可用），遇到需要放行的操作应当停止并回报，由你在上层处理。
- 工作目录常不是 git 仓库，也常没有测试套件：验收判据要条件化——有测试运行器就跑它，
  否则退化为「产物存在 + 命令输出符合预期」的等价证据。
