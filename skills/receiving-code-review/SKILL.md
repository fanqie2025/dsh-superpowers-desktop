# 接收代码评审（receiving-code-review）

收到评审意见时，默认动作既不是照单全收，也不是顶回去，而是**技术核实**。核心原则：**先核实再动手，先问再假设，技术正确性优先于社交舒适。** 评审意见是待验证的假设，不是判决。

## 何时用 / 何时不用

**用**：任何评审意见到手之后、动手改之前；意见含糊或技术上可疑时；意见与你已知的架构决策冲突时；`subagent-driven-development` 每个任务收尾、紧接 `requesting-code-review` 之后。

**不用**：改动本身还没成形（先做完再送审）；你自己在写评审意见（那是 `requesting-code-review`）。

## 核心原则

1. **先核实，再动手。** 意见可能基于过时信息：它看的是某个快照，而你在那之后已经改过。先 `read`／`grep` 看当前代码，再决定改不改。
2. **三类分流，处置方式不同**：

   | 类别 | 特征 | 处置 |
   |---|---|---|
   | **必须改** | 真缺陷：会崩、安全、破坏既有功能，或明确违反需求/计划 | 无争议，进队列 |
   | **可以讨论** | 取舍分歧：命名、抽象层次、性能 vs 可读性、要不要砍某个功能 | 用**判据**争论：需求原文、既有约定、实测数据、平台约束 |
   | **不该改** | 基于误解：评审者缺上下文、看的是旧版本、把有意设计当缺陷 | 用证据说明，并**记录在案**，不是沉默照做 |

3. **不辩解、不表演式顺从。** 禁止「你说得完全对！」「好建议！」「谢谢指出！」——以及任何道谢，以及核实之前的「我这就改」。想写「Thanks」就删掉，改成陈述你核实了什么、改了什么。
4. **每条意见都要有归宿**：改了（+位置）、不改（+理由）、待确认。整段跳过，或含糊带过（「部分采纳」而说不清哪部分），都算没回应。
5. **改完要重新验证**：修评审意见本身也会引入回归。

## 流程

1. **读完再说话。** 一次读完整份反馈，不边读边回应。
   判据：能把每条用一句话复述成「它要求什么」。
2. **复述理解，先澄清不清楚的项。** 只要有任何一条不清楚就 **STOP**：先问清全部不清楚的项，再动手任何一条——意见之间常互相关联，理解一半等于改错。
   例：评审说「修 1–6」，你明白 1、2、3、6，不清楚 4、5 → 先问清 4、5，再动手；**不要**先改 1、2、3、6 再说。评审者是 `subagent` 时，补齐它缺的信息本身就是澄清的一部分。
   判据：拿到能据以动手的答复。
3. **核实事实（对着代码库，不是对着意见）。** 逐条做：`read` 相关文件的当前内容；`grep` 查它提到的函数/接口/常量还有谁在用、是否真的没人调用；核对需求或计划原文，看是否与已定决策冲突；确认意见针对的版本是否仍是当前版本（是 git 仓库就用 `pwsh` 取 `git log -1 --format=%h -- <path>`，不是就对照改动前后的文件内容）。
   判据：每条都能说出「在当前代码上成立／不成立」及其依据（`路径:行号` 或命令输出）。
4. **分流并逐条给出归宿。** 产出一张表：编号｜意见摘要｜归类（必须改/可以讨论/不该改）｜归宿（已改／不改+理由／待确认）｜证据。
   判据：**表行数 = 意见条数**，没有空归宿。
   判「可以讨论」时必须说得出判据（需求原文、实测数据、平台约束）；说不出来说明还没核实够，退回第 3 步。
5. **按顺序动手，一次一条。** 顺序：阻塞性问题（崩溃、安全、破坏既有功能）→ 简单修（错字、导入、命名）→ 复杂修（重构、逻辑）。每条单独验证。
   判据：每条改完都有对应的验证输出，不是攒一堆最后一起跑。
6. **改完重新验证（回归）。** 重跑原本通过的验证，并额外重跑这条意见碰到的那几个调用方。
   判据：给出命令与原始输出；本机常常没有测试运行器，此时写明等价验证是什么（调用点逐一 `read` 对照、手工复现步骤与结果）。
7. **回复只讲技术，且落在原线程。** 改了什么（`路径:行号`）、为什么这么改、哪条不改及理由、哪条待确认。别另起一处讨论。
   判据：每条意见在回复里都有对应的一句。
8. **自己顶错了要纠正。** 核实后发现评审是对的：「我查了 X，它确实是 Y，现在改」——不长篇道歉，不为当初的反驳辩护。
9. **顶回去的判据。** 建议会破坏既有功能／评审者缺上下文／违反 YAGNI（`grep` 证明没人调用）／在当前技术栈下技术上不成立／有兼容或遗留理由／与用户已定的架构决策冲突。前五条用技术理由顶，引用能跑的测试或代码；**冲突类不在评审线程里解决，用 `ask_user_question` 交用户裁决**。无法核实时直说「没有 X 我核实不了，你要我调查／去问／先做？」，不要猜着改。

## 反模式

- **表演式认同**（「你说得完全对！」「好建议！」）——上游点名的第一条禁令。
- **任何道谢**（「谢谢指出」）：动作本身就是回应。
- **未核实就动手**：意见基于旧快照时，照改等于亲手制造回归。
- **一次全改完再一起测**：出了回归也无法定位是哪条改坏的。
- **含糊的「部分采纳」**、整段跳过、只回能反驳的那几条。
- **不敢顶**：把技术问题藏起来，比说错更贵。
- **不清楚也先改**：会连带把相关的几条一起改错。

## 完成判据

- 每条意见都有明确归宿（已改／不改+理由／待确认），条数与回复条数对齐，无遗漏。
- 每条「不改」都附证据（`路径:行号`、`grep` 结果、命令输出、需求原文引用），不是「我觉得不用」。
- 每条「已改」都附改后位置与验证输出。
- 全文没有表演式认同句，也没有道谢句。
- 不清楚的项在动手前已澄清，不是边改边问。
- 改动后已重跑验证并给出命令与原始输出（无测试运行器时给出等价验证及其结果）。
- 与用户既有决策冲突的项已升级给用户，未自行拍板。

## 与其它技能的关系

- 配对技能是 **`requesting-code-review`**（发的一方）：它管「怎么发起一次值得做的评审」，本技能管「收到之后怎么核实、分流、反驳、闭环」。
- 链路：`subagent-driven-development` 每个任务 → `requesting-code-review` → **本技能** → 重新验证 → 下一个任务。
- 意见指向「实现偏离计划」时，回去看 `writing-plans` 的计划原文；要定位「为什么坏」的根因用 `systematic-debugging`；被要求补复现或测试时配合 `test-driven-development`；大范围返工先用 `todo_write` 列出来。

## 本机适配注意

- 评审者常是 `subagent` 起的**独立上下文**，它看不到你的会话、推理和试错。所以它误解是常态、不是失职：回应时主动补齐它缺的信息（当前文件内容、需求原文、你已确认的平台约束），不要默认它「应该知道」。
- 上游「外部评审者」五问就是第 3 步的核实清单：对本代码库技术上是否成立／会不会破坏既有功能／当前实现为什么是这样／在目标平台与版本上是否都成立／评审者是否掌握全部上下文。逐条问过去，再决定改还是顶。
- 用户本人的反馈视为可信（范围不清仍要问），但同样不表演式认同、不道谢，直接讲你核实和改了什么。
- **工作目录通常不是 git 仓库**：第 3 步的版本核对与第 6 步的回归验证写成条件式——没有 git 就用改动前后的文件内容＋命令输出作等价证据；**退化后判据不变**，仍要能证明「意见针对的仍是当前版本」「改完没弄坏别的」。
- `pwsh` 有已知故障：可能返回 `0xC0000142` 且零 stdout（与沙箱拒绝 `[sandbox: file access denied ...]` 是两种形态）。遇到时不要反复重试同一条命令，改用 `read`／`grep`／`glob` 继续取证；确需执行程序再请用户放行。
