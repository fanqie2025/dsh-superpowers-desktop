# 测试驱动开发（TDD）

先写测试，看着它失败，再写最小实现让它通过，最后在保持全绿的前提下重构。**核心原则：没亲眼看着测试失败，你就不知道它到底在测什么**——没失败过的"通过"什么也证明不了。违反字面规则就是违反规则本意。

## 何时用 / 何时不用

必须用：新增功能、修 bug、重构、任何行为变更。
例外（先问用户）：一次性丢弃的验证脚本、生成出来的代码、纯配置文件。
"这次就跳过 TDD"——停，这是合理化，不是判断。

## 铁律

```
没有先失败的测试，就没有生产代码。
```

先写了实现？删掉，从测试重来。不许留作"参考"、不许边写测试边"顺手改改"、不许再去看它。删除就是删除。

## 流程：RED → GREEN → REFACTOR（顺序不可颠倒）

**1. RED —— 写一个会失败的测试。** 一个行为、名字说清行为、测真实代码。用 `write` / `edit` 落盘。

**2. 验证 RED —— 亲眼看到它失败（强制，绝不跳过）。** 用 `pwsh` 跑它，确认：确实失败（不是报错崩掉）、失败信息就是预期的、失败原因是功能缺失。判据是把失败输出实际读出来。测试直接通过 → 你在测已有行为，改测试；报语法/导入错 → 先修到"能跑但失败"。

**3. GREEN —— 写最小实现让它通过。** 只写刚好够过的，不加功能、不顺手重构别处。

**4. 验证 GREEN —— 亲眼看到它通过（强制）。** 判据：测试通过、其它测试仍通过、输出干净（无 error/warning）。还失败 → 改实现，不改测试；别的挂了 → 现在就修。"其它测试"指项目全套，不只是你写的那一个文件：任务范围限定的是交付物，不是验证范围。跑出来的失败都要在报告里点名，包括不是你造成的——看见了不提就是漏报。

**5. REFACTOR —— 只在绿了之后。** 去重、改名字、抽辅助函数；不新增行为；重构后再跑一次，仍须全绿。

**6. 重复。** 下一个行为，下一个失败测试。

## 为什么"先写实现再补测试"不算 TDD

补的测试一上来就通过，而没失败过的"通过"什么也证明不了：它可能测错对象、测的是实现细节而非行为、恰好漏掉你没想到的边界。你从没看它失败，就没证明它抓得住这个 bug。

更根本的是提问方向不同——**测试后写回答"这段代码做了什么"，测试先写回答"它应该做什么"**；后写的测试已被你的实现带偏，只验证你记得的情况，而不是测试逼你发现的情况。那是覆盖率，不是证据。"手动试过了"也不成立（临时、无记录、改一次就重来）。"花了几小时不舍得删"是沉没成本：真正的选择是按 TDD 重写（高可信）还是留着补测试（低可信）。

## 写不出失败测试 = 需求没想清

这是 TDD 最有价值的副产品：**写不出能让当前代码失败的测试/验证，通常不是"没什么可测"，而是你还没想清要什么、边界在哪、什么叫对。**测试写不下去是设计信号。

不知道怎么测 → 先写出期望的调用方式或先写断言，或问用户；测试太复杂 → 接口太复杂，简化设计；必须 mock 一切 → 耦合太重，改依赖注入；前置准备巨大 → 抽辅助，仍复杂就简化设计。把"难测"听成"这个设计难用"。

## 本机退化：没有测试运行器、甚至不是代码仓库

本工作区经常不是 git 仓库，也没有测试框架。**退化不等于豁免**：把"可执行的测试"换成"可执行的验证命令 / 可观察的输出"，门禁一条不减——**没有判据就不算完成**。

三种可接受形态（都要在动手改之前先跑一次，看到它不成立）：

1. **可复现的 PowerShell 校验**：断言并打印期望值与实际值，例如
   `pwsh -NoProfile -Command "$g=(Get-Content .\out.json -Raw|ConvertFrom-Json).count; if($g -ne 3){'FAIL got '+$g; exit 1}else{'PASS'}"` —— 改前必须打印 `FAIL`，改后必须打印 `PASS`。
2. **一次真实调用**：真跑一次并读实际输出（状态码、stdout、退出码、文件内容），例如
   `curl.exe --noproxy '*' -s -o NUL -w "%{http_code}" http://127.0.0.1:PORT/health`（本机 `http_proxy` 会伪造 502，必须 `--noproxy`）。
3. **明确的输入输出对照**：给定输入 → 期望输出列成表，改前改后各核一遍，写清哪几行由 FAIL 变 PASS。视觉结果用 `read_image` 读实际产物比对。

退化后的判据清单（缺一不可）：

- [ ] 验证方式在动手改之前**真的执行过**，并看到"不满足"的实际输出；
- [ ] 该输出被真实读到并写进结论，不是"应该会失败"的推断；
- [ ] 有明确的通过/失败判据（数值、字符串、状态码、退出码），不是"看起来对了"；
- [ ] 命令可重复执行，别人照着能复现同一结论；
- [ ] 改完重跑同一命令，从 FAIL 变 PASS；
- [ ] 结论写明"跑了什么、看到什么"。

判据失败要分清：`[sandbox: file access denied ...]` 是沙箱拒绝，`pwsh` 返回 `0xC0000142` 且零 stdout 是执行器故障——**都不是"验证通过"，也不算"跑过了"**。遇到后者别反复重试同一条命令，改用 `read`/`write`/`edit`/`glob`/`grep` 做静态核验（如逐行核对产物），或请用户放行后再执行。是 git 仓库时先确认工作区状态、必要时用分支隔离；不是就跳过这步，"先失败后通过"的证据不能省。

## 反模式 / 红旗（出现即停，删码重来）

先实现后测试；测试一写就通过；说不出这次为什么失败；一次改多处；绿之前就重构；为了通过去改测试而不是改实现。
"太简单不用测""稍后补""手动测过了""补测试效果一样""讲精神不讲仪式""留作参考""花了几小时删了可惜""我务实一点""这次情况特殊"。

## 完成判据

- [ ] 每个新函数/行为都有对应的测试或验证；
- [ ] 每个测试/验证在实现之前被**亲眼看到失败**（RED 证据）；
- [ ] 失败原因是功能缺失，不是拼写或环境错误；
- [ ] 只写了刚好通过的最小实现；
- [ ] 全部通过（含项目原有测试/既有验证），输出干净；
- [ ] 重构之后仍然通过；
- [ ] 用真实代码/真实调用，mock 仅在不得已时；
- [ ] 边界与错误路径有覆盖。

框打不齐就是跳过了 TDD，不是"差不多"。

## 与其它技能的关系

需求没想清、写不出失败测试 → 先 `brainstorming` 再 `writing-plans`；方案已定要铺开 → `writing-plans` → `subagent-driven-development`（每个子任务自带 RED 证据）；修 bug 先写复现测试再进本流程；要把产物交给用户时用 `present`。

## 本机适配注意

- 一律用 `pwsh`（PowerShell 语法），没有 Bash。
- 文件策略常为 `workspace-write`：只有会话工作区可写，工作区外路径会被沙箱拒绝；验证产物写在工作区内。
- `pwsh` 返回 `0xC0000142`、零 stdout 是已知故障，既不是判据失败也不是成功。
- 工作区常常不是 git 仓库、没有测试套件——按上面的条件式退化执行，判据清单照旧。
