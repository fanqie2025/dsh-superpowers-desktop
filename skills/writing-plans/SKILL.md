# 编写实现计划（writing-plans）

把已经获批的设计翻译成一份计划，交给一个**没看过这个仓库、也没看过这份设计**的执行者。他懂这门语言的惯用写法，只要给他确切的接口和确切的判据，他就能自己补出合理的实现；他补不出来的是你的决定：动哪些文件、叫什么名字、什么签名、设计里钉死了哪些取值、每项任务靠什么证明自己做对了。计划就是把这些写下来。

## 何时用 / 何时不用

**用**：设计已获批、任务多步、改动会落到多处或会跨会话；有别人（或另一个 subagent）要接手；出了错代价高。用户说「拆任务」「写个计划」「先出方案再动手」时也走这里。

**不用**：设计本身还没定（回到 `brainstorming`，别用计划掩盖没想清的设计）；改动可以一次说完、无所谓交接（见下面的轻量退化形态）。

## 核心原则

1. **一项任务 = 一个可独立校验的结果。** 任务边界划在「一个评审者可以否掉这一项，同时批准相邻那项」的地方。上游用「2–5 分钟」形容粒度，那只是经验值；本机的判据是**可独立校验**——这项任务自己有验收判据，不通过时能被单独打回。
2. **每项任务必须带明确的验收判据**：跑什么、看什么输出、什么算过。
3. **计划只写执行者无法独自决定的事**：文件、名字与签名、设计里钉死的取值、证明用的检查。签名和测试已经决定的函数正文不该出现在计划里。
4. **先锁文件结构，再切任务。** 每个文件一个清晰职责；一起改的文件放一起（按职责拆，不按技术层次拆）；既有仓库沿用既有模式，不擅自重构。
5. **计划比它描述的代码还长，就说明你写了代码，而不是计划。**

## 流程

1. **确认设计已获批并读它**（`read`）。判据：能用一句话说出目标、架构，以及设计里已经钉死的取值。
2. **范围检查**：若设计覆盖多个互相独立的子系统，拆成多个计划，一个子系统一份；每份自身要能产出可运行、可校验的成果。
3. **锁定文件结构**：列出要创建/修改的文件和各自职责。判据：改动清单齐全，且每个文件只有一个职责。
4. **切任务**。把脚手架、配置、文档折进真正需要它们的那个任务，不要单独成项。每项任务写清两块：
   - **Files**：Create / Modify（给出精确路径，能带行号就带）/ Test。
   - **Interfaces**：Consumes（用到前面哪项任务的什么，给确切签名）、Produces（后面任务依赖的确切函数名、参数与返回类型）。执行者只看得到自己那一项，这是他知道邻居用了什么名字的唯一途径。
5. **写步骤**：每步一个动作 + 一个可检查的结果。测试步给测试名与断言（含设计里的确切取值）；代码步给确切签名、所在文件、设计钉死的取值，正文留给执行者（只有签名与测试定不下来的算法，或设计规定要逐字照抄的文案，才贴正文）；验证步给命令与「什么输出算通过」。
6. **写计划头部**：目标（一句话）、架构（2–3 句）、技术栈、**设计文档路径**（计划是从设计论证出来的，设计要跟着走）、**全局约束**（设计里的项目级要求，逐字抄取值）、**评审聚焦**（设计暗示、但没有任何任务的检查覆盖到、最容易让人踩坑的 5 类输入或失败模式，各一行，最可能的排最前；写完再把对应的检查补进拥有那段代码的任务里）。
7. **自检**（自己跑一遍，不要派 subagent）：
   - **覆盖**：设计里每条要求都指得出一个任务，缺口列出来。
   - **步骤扫描**：每步只让人做恰好一件合理的事；「什么都不决定」的行（TBD、处理边界情况、补充测试、加适当校验）和「抄写正文」的行都要修。
   - **类型一致**：后面任务用的类型、签名、属性名与前面定义的一致（前面叫 `clearLayers()`、后面叫 `clearFullLayers()` 就是 bug）。
   - **评审聚焦**：每一行都落进了某个任务的检查；空着表示查过没有，不是跳过检查。
   - **比例**：计划比设计长好几倍时，把正文换成签名、测试名与断言。
   就地修改，不必重审。
8. **落盘**（`write`）：写到 **`<工作区>/plans/YYYY-MM-DD-<主题>.md`**。上游默认是 `docs/superpowers/plans/`，本机改用工作区内的 `plans/`，用户的指定优先。用 `glob` 看一眼 `plans/` 里有没有既有计划，沿用它的命名。判据：文件写成功，且路径在会话工作区内。
9. **用 `todo_write` 同步成可勾选清单**：每项任务一条 todo；写完计划立刻同步，执行期逐条推进。计划正文里的步骤保留 `- [ ]` 复选框写法，与 todo 一一对应。
10. **交接**：把计划路径交给人类过目，确认它就是要的东西，然后选执行方式。
    - **subagent 驱动**：每个任务由一个 fresh subagent 实现、另一个 fresh subagent 复查，最后整份复查一遍；最彻底，代价是每项任务、每次复查都吃一个新上下文 → 加载 `subagent-driven-development`。
    - **本会话顺序执行**：我在本会话里逐项实现，结束时让一个 fresh reviewer 复查；最省最快，但没有中途的独立复查 → 加载 `executing-plans`。
    推荐哪一种，用一句话说出理由（任务之间接口咬合多紧、有几项、做错了要付什么代价）。**等人类确认后再动代码。**

## 轻量退化形态

不是每个任务都值得一份计划文件。以下**全部**满足时不写文件：步骤 ≤3；没有跨任务的接口决策（不需要 Interfaces 块）；改动可逆、出错代价低；一个会话内做得完。此时口头列出 3 步 + 用 `todo_write` 记成清单，每步仍要说清「做什么、怎么知道成了」。

任何一条不满足（涉及多个子系统、有别人接手、需要独立复查、会跨会话、设计里有钉死的取值要对齐）就回到完整计划。

## 反模式

- **任务没有验收判据**：「实现 X 功能」「处理边界情况」「补充测试」「加适当的校验」——这些行什么都不决定，执行者只能猜。
- **按时间片而不是按可校验结果切任务**：评审者无处下手，打不回任何一项。
- **把函数正文抄进计划**：计划比代码长，等于替执行者写完了代码，也让他失去了自己判断的余地。
- **名字/签名前后不一致**：后面任务调用了一个前面从没定义过的函数。
- **跳过自检直接交接**：尤其跳过「覆盖」和「评审聚焦」。
- **计划写到工作区外**：沙箱会直接拒绝。
- **设计还没获批就开写**：回到 `brainstorming`。

## 完成判据

- 计划文件存在于 `<工作区>/plans/YYYY-MM-DD-<主题>.md`，`write` 返回成功。
- 设计里的每条要求都能指到某个任务；评审聚焦里每一行都有对应的检查落进某个任务。
- 每项任务都有 Files、Interfaces，以及可核验的验收判据（命令 + 期望输出，或等价的检查）。
- `todo_write` 的条目与计划里的任务一一对应。
- 自检 5 项都跑过，发现的问题已就地修完。
- 人类已过目计划并选定了执行方式。

## 与其它技能的关系

`brainstorming`（产出并获批设计）→ **`writing-plans`** → `subagent-driven-development` 或 `executing-plans`。若本机是 git 仓库且需要隔离工作区，隔离在**执行阶段**按上游的 `using-git-worktrees` 建立，不在写计划时建。

## 本机适配注意

- **可写范围**：本机文件策略常为 `workspace-write`，只有会话工作区可写。工作区外的路径（`C:\Users\...\.dsh\profiles\...`、知识库磁盘等）会被沙箱拒绝，报 `[sandbox: file access denied ...]`。所以计划落在 `<工作区>/plans/`，别照抄上游的 `docs/superpowers/plans/`。
- **工作目录通常不是 git 仓库**，也常常没有测试运行器。带 commit 的收尾步骤写成条件式：是 git 仓库就每项任务收尾提交一次；不是就删掉这一步，改用「文件已保存 + 验收检查通过」作为收尾判据——不要写一个跑不起来的提交步骤，也不要假装提交过。
- **TDD 步骤要能退化**：没有测试运行器时，「先写失败测试、跑一遍看它失败」退化为「用 `read` / `grep` / `pwsh` 证明当前行为不满足判据」；等价判据是**有证据表明改动前确实不满足**，而不是凭印象。
- **`pwsh` 有已知故障**：可能返回 `0xC0000142` 且零 stdout（这与沙箱拒绝是两种形态）。遇到时不要反复重试同一条命令，改用 `read`/`write`/`edit`/`glob`/`grep` 继续取证；确需执行程序再请用户放行。验收判据尽量选这几样工具能看到的证据。
