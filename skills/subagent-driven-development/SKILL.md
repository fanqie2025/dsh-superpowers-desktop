# 子智能体驱动开发

别用一个上下文把计划做完：**每任务派一个全新上下文的子智能体实现，完成即刻做两阶段评审（先规格符合性、再代码质量），全部做完再整支终审**。子智能体只拿到你构造的上下文，你的上下文留给协调与裁决；没有评审的执行只是未经校验的改动堆积。

用：有实现计划（`writing-plans` 产出）、任务基本独立能逐个验收、要连续跑到完。不用：没有计划或任务紧耦合到无法逐个验收 → 先 `brainstorming` / `writing-plans`；只有一两个小改 → 直接做。

## 核心原则
一任务一实现者，上下文全新；**评审者不能是作者本人**，评审一律用 `subagent` 另起新上下文、**别用 `subagent_fork`**（会把你的会话视角带进去），自评只是自评；**每个任务完成后立即校验**，绝不攒到最后一起验，终审是补充不是替代；评审分**两阶段**——先规格符合性（是否恰好实现了所要求的，不多不少）、再质量，两个裁决都要拿到；**账本 > 记忆**，完成/修复轮次/裁决都写进账本文件，别只靠 `todo_write`；**裁决而不是停顿**，按"规格是权威、计划是它的论证"裁决冲突与计划缺陷，记 `裁定: <决定> — <理由> — <错了的代价>`，只有四类停下问人：不可逆操作、安全敏感动作、工作区外副作用、计划烂到每条路都是猜。

## 工具判据（本机）
- 自包含的实现或评审 → `subagent`（**新上下文，看不到本会话和你的中间推理**，提示词必须自包含）；要本会话已有结论才用 `subagent_fork`（继承已完成轮次），**评审别用**；追问 `send_message`、停掉 `interrupt_agent`、查状态 `list_agents`。
- **`workflow` 门槛写死**：只有"大规模扇出"（十几个到上百个**独立单元**、要并发或分阶段编排）才值得写 JS 编排脚本；**一两个委派一律用 `subagent`**——本技能循环天然串行，用不上它。本机 `subagent` 无 model 参数，靠**任务粒度**控成本（机械小改合成一批，需要判断的拆开派）。

## 流程

### 0. 准备
- 判据不是 git，而是"能否给出可复核的改动证据"：是 git 仓库 → 记下派发前 `BASE`，评审包用 `git diff BASE..HEAD`；不是 → **文件级评审包**（用 `write` 落一份改动清单、关键片段、跑过的命令与输出）。
- 账本 `<工作区>/.sdd/<计划名>-progress.md`，首行 `# 执行台账 — 计划: <计划文件路径>`；首行对得上同一计划就接着跑——`任务 <N>: 完成` 的**别重派**、末行是修复轮次的从下一轮起。通读计划、记下全局约束，用 `todo_write` 给每个任务建 todo。
- **预检扫描**（派发任务 1 前）：查互相矛盾的任务、与全局约束冲突的条目、计划要求却会被评审当缺陷的东西（断言为空的测试、逐字复制的逻辑块），产出**一张表**进账本：共享文件或接口的任务对各一行、每个任务各一行。"扫描干净"而没有这些行等于没扫。

### 1. 派发实现者
子智能体**看不到你的中间推理与会话历史**，提示词必须自包含，六要素缺一不可：**背景**（任务位置、依赖的已定接口）、**目标**（任务原文给全，含精确取值、签名、测试用例）、**约束**（任务边界、全局约束、不许越界重构）、**判据**（什么算完成、跑什么看什么）、**交付物**（改哪些文件、报告写到哪）、**回报格式**（见下）。别粘累积的历史摘要，也别让它读整份计划。单次只描述一个任务；**同形小改**合成一批给一个子智能体、其 diff 当一个单元评审。**绝不并行派发多个实现者**。记下返回的 agent id（回环靠 `send_message` 找回）。禁止它再派子智能体，**尤其不许自己派评审者**（那是重复的一整份、不计入流程）。
**回报契约**：全文写进报告文件，只回 ≤15 行——`Status: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT`、改动清单、一行测试摘要、疑虑、报告文件路径。

### 2. 处理回报
**DONE** → 进第 3 步。**DONE_WITH_CONCERNS** → 先读疑虑，涉及正确性或范围的先处理。**NEEDS_CONTEXT** → 补上下文后重派。**BLOCKED** → 先定性：上下文问题→补上下文；要更强推理→拆小或换更强编排；太大→拆；**计划本身错→你裁决、记账，把裁决带进重派**。绝不在毫无改变时让同一模型硬重试。

### 3. 立即评审（两阶段，评审者=新上下文）
门禁核心：不许跳过，也不接受只给一个裁决的报告。
- **评审包**：用 `pwsh` 把 `git log --oneline`、`git diff --stat`、`git diff -U10` 写进**一个**文件，只把**路径**给评审者（diff 不进你的上下文）；非 git 用第 0 步的文件级包。
- **派发**：`subagent` 新上下文，给任务原文、实现者报告路径、评审包路径、**逐字抄来的全局约束**（精确取值、格式、组件间关系）。
- **规格符合性**：查**缺**（漏做或声称做了没做）、**多**（没要求的、过度设计）、**偏**（方向对但做错事）；批式派发逐文件核对，漏掉的文件无论其余多干净都算"缺"；只凭 diff 判不了的标 ⚠️ 交回**你自己**核实，为真缺口即评审失败、进回环。
- **质量**：关注点分离、错误处理、DRY 而非过早抽象、边界情况；测试验证真实行为而非 mock；文件职责单一。用 `文件:行` 给证据。
- **评审者规矩**（写进提示词）：报告是**未经验证的主张**、要对着 diff 核；不重跑实现者跑过的测试（除非读代码生疑，且只跑聚焦用例）；不爬代码库；只读、不许改工作区；**不许再派子智能体**；不许预判（别写"这不算缺陷""最多 Minor""计划就是这么选的"）。

### 4. 修复回环（最多 5 轮）
触发：规格 ❌、任何 Critical/Important finding、或你核实为真的 ⚠️。**Minor 不进环**，记 `任务 <N>: 次要（延后）: <一句话>` 留终审分诊；**与计划原文冲突的 finding**（含 plan-mandated）由你裁决，不能无裁决记录就派发与计划矛盾的修复。
每轮 = 一次修复 + 一次定向复审。**第 1–3 轮**用 `send_message` 找回原实现者、给 finding **原文**；不可达就带"任务原文 + 报告路径 + findings"重派新 `subagent`（报告文件是两条路线共用的持久记忆）。**第 4–5 轮**换**新上下文**并框定"已有实现者尝试 N 次，现在归你，先读报告文件看试过什么"。**每轮都要**重跑覆盖被改代码的测试、把修复报告**追加**到同一报告文件（改了什么、覆盖测试、命令、输出），这三样不全就别重派复审。**定向复审**同样起 `subagent` 新上下文，只给 findings 列表、任务原文、报告文件、**修复区间** diff；逐条判 `ADDRESSED | NOT ADDRESSED`（"尝试了"不算解决），只看修复 diff 有无新的 Critical/Important，范围外观察记 次要（延后）、**不延长回环**。每轮记账 `任务 <N>: 修复第 <R>/5 轮（已解决 <X>，未决 <Y>）`。**别自己在协调会话里动手修**（污染上下文且跳过评审）。
**熔断**：第 5 轮仍有未决 finding → 停止派发、自己逐条裁决：评审者错了或本就可争 → `任务 <N>: 挂起 — <finding> — 裁定: <为什么保留现状>`；真实但下游无人依赖 → 同样挂起并写明"真实、延后"；真实且**承重**（下游建在它上面或暴露计划缺陷）→ 裁决**能解开依赖的最小改动**、记账、带进下一任务。**只许在熔断点裁决**（提前裁决是换了名字的预判），每条裁决必须进账本。

### 5. 收尾该任务
复审干净（或熔断后每条未决 finding 都已带裁决挂起）→ 账本追加 `任务 <N>: 完成（提交 <base7>..<head7>，评审干净）`（熔断过的写 `<K> 挂起`），此时才标记 todo 完成。**只要还有未修、也未带裁决挂起的 Critical/Important，就不许进下一个任务。**

## 整支终审
备整支范围的包（`git merge-base main HEAD` 到 `HEAD`；非 git 用文件级清单），用 `subagent` 新上下文派发——最需要判断力的一次评审——把账本里所有 `次要（延后）` 与 `挂起` 行指给它分诊。有 finding → **只派一次**修复（整份列表给**一个**子智能体），随后**恰好一次**定向复审，残余项按熔断规则处理。**没有第二轮修复波**；残余的承重问题在收尾时交回给人。

## 反模式
| 借口 | 现实 |
|---|---|
| "规格差不多就得了" | 规格有缺口 = 没做完：修掉，或到熔断点裁决。 |
| "我自己顺手修了" | 协调者动手污染上下文且跳过评审。 |
| "再来一轮就收敛了" | 过了熔断点不会收敛，失败是结构性的。 |
| "修复很小，跳过复审" | 未评审的修复正是回归落地的方式。 |

## 完成判据
- 账本里每个任务都有 `任务 <N>: 完成` 行，且**没有任务只有实现、没有两阶段评审记录**。
- 每份任务评审都给出**两个裁决**（规格 ✅/❌ 与质量 Approved/Needs fixes）；出现 ❌ 的有闭环（修复轮次 + 定向复审逐条 `ADDRESSED`）。
- 终审跑过一次整支范围评审且 findings 有闭环；账本、报告、评审包留在工作区内可复核，每条 `裁定:` 都进了最终交付信息的"我做的裁决"清单。

## 与其它技能的关系
`brainstorming` → `writing-plans` → **本技能** → `requesting-code-review` → `finishing-a-development-branch`。上游的 implementer / task-reviewer / re-review 模板与 `scripts/` **未移植**。

## 本机适配注意
- 子智能体**同样受 `workspace-write` 沙箱约束**，只有会话工作区可写：报告与账本路径必须在工作区内。
- **别假设子智能体能跑 `pwsh`**：可能返回 `0xC0000142` 且零 stdout；派发时写清"跑不了命令时怎么给证据"（改用 `read`/`grep` 并说明未运行），派评审时别把"必须重跑测试"当门禁。
- `subagent` **看不到你的中间推理**——既是本技能成立的前提，也是它唯一的坑。
- 工作目录常常不是 git 仓库、也没有测试套件：此时"立即校验"退化为**文件级评审包 + 定向复核**，判据是"评审者仅凭它和改动文件就能给出两个裁决"。
