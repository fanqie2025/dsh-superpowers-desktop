# 收尾一个开发分支

**核心顺序：验证全绿 → 看清 diff → 检测环境 → 由人选择交付形态 → 执行 → 清理。** 收尾不是"跑完测试就合掉"，而是一道道门禁：没验证完不合、没逐块看过改动不合、无关改动没拆出去不合——"可以合了"是个结论，得出示证据。收尾阶段犯的错（合进错的分支、删掉别人的 worktree、`--force` 掉只存在于 worktree 里的笔记）几乎都不可逆。

开工时说一句：「我正在用 finishing-a-development-branch 技能收尾这份工作。」

## 何时用 / 何时不用

**用**：实现完成、准备交付；要决定一个分支的去留；合并前；建 PR 前；清理隔离工作区。
**不用**：实现还没完、测试还红（先修）；只是读代码查资料。
本机最常见的形态是**工作区不是 git 仓库**：此时 git 部分整体退化，按「本机适配注意」的交付前检查清单走，交付物就是工作区里的最终文件。

## 核心原则

1. **先验证，后谈交付**：红灯时只有报告，没有菜单。
2. **diff 是门禁，不是仪式**：没逐块看过要合进去的改动，就没有"可以合了"这个结论。
3. **交付形态由人拍板**：合并、建 PR、保留分支是**并列**选项，不是难度递增的默认路径。
4. **丢弃只由明确请求触发**，按字面确认；`--force` 永远不是自己的主意。
5. **只清理自己创建的东西**，宿主的工作区不碰。

## 流程

### 第 1 步：验证测试（门禁一）

跑项目自己的测试（`npm test` / `cargo test` / `pytest` / `go test ./...`）。

- **有失败 → 停下，只报告失败，不给菜单**：「测试 <N> 项失败，收尾前必须修复」+ 失败摘要。
- **全绿 → 进入第 2 步。**
- **没有测试运行器 → 明说"无测试套件"**，退化为「构建成功 + 静态检查干净 + 手动跑通关键路径」，并逐条给出证据。不许把"没得跑"当成"通过了"。

证据必须是**本轮**跑出来的：上轮绿过、子代理说过了，都不算。

### 第 2 步：看清 diff（门禁二）

```powershell
git status --short              # 有没有未提交 / 未跟踪的意外文件
git diff; git diff --staged     # 未暂存 / 已暂存的改动，逐块看
git log --oneline <base>..HEAD  # 这段分支上到底有哪些提交
```

逐块读过改动，再回答三件事：

- **临时调试代码、死代码清了吗**？`console.log` / `print` / 断点 / 临时注释 / 写死的路径与端口 / 注释掉的代码块 / 废弃文件——清干净再往下走。
- **有没有无意中的改动**？被顺手改掉的无关文件、整文件格式化重排、误删的依赖、调试期改的配置。**发现了就拆出去**：单独成一次提交或还原，别夹带进这次交付。
- **文档同步了吗**？行为、参数、用法变了就同步 README / 注释 / 变更记录；确实不用改，就明确说"文档无需变更"。

判据：能一句话说清"这次交付包含哪些改动、每个改动为什么在这里"。说不清就是门禁没过。

### 第 3 步：检测环境（决定菜单与清理方式）

```powershell
$gitDir    = git rev-parse --git-dir
$gitCommon = git rev-parse --git-common-dir
$worktree  = git rev-parse --show-toplevel   # 先取值；第 6 步会切走目录
```

| 状态 | 菜单 | 清理 |
|---|---|---|
| `$gitDir -eq $gitCommon`（普通仓库） | 标准 3 选项 | 无 worktree 可清 |
| 不等 + 命名分支 | 标准 3 选项 | 按来源判断（第 7 步） |
| 不等 + detached HEAD | 精简 2 选项（无合并） | 外部托管，原地不动 |

### 第 4 步：确定基线分支

基线 = 这份工作从哪分出来的，通常在计划、对话或分支的 upstream 里写着。不确定就**用 `ask_user_question` 问**：「这个分支是从 <最佳猜测> 分出来的，对吗？」合进错的分支，撤销代价很高。

### 第 5 步：让人选交付形态

普通仓库 / 命名分支的 worktree，**原样给出这 3 项**（用 `ask_user_question`，不要替用户选）：

```
实现已完成。你想怎么处理？
1. 本地合并回 <基线分支>
2. 推送并创建 Pull Request
3. 原样保留这个分支（我自己稍后处理）
```

detached HEAD 时**只给这 2 项**：①推送为新分支并创建 Pull Request ②原样保留。
**丢弃不出现在菜单里**：只有用户明确说要扔掉这份工作，才走丢弃流程。等他们回答——集成方式是他们的决定。

### 第 6 步：执行选择

**选项 1 · 本地合并**

```powershell
$mainRoot = git -C (Join-Path (git rev-parse --git-common-dir) '..') rev-parse --show-toplevel
Set-Location $mainRoot            # 先离开 worktree，才能删它
git checkout <基线分支>; git pull; git merge <功能分支>
<测试命令>                        # 合并结果上再跑一遍
```

合并结果测试失败 → **停手**，worktree 与分支原地保留，先排查：此时什么都没推，合并是本地的、可回退。合并结果全绿 → 走第 7 步清理，再 `git branch -d <功能分支>`。

**选项 2 · 推送并建 PR**

```powershell
git push -u origin <功能分支>
# detached HEAD：git push origin HEAD:refs/heads/<新分支名>
```

再用托管平台的 CLI 或推送时打印的创建链接，按仓库的 PR 模板对着 `<基线分支>` 建 PR，并把 URL 回报用户。**worktree 保留**——评审意见就在那里改。

**选项 3 · 原样保留**：报告「保留分支 `<名>`，worktree 在 `<路径>`」。

**用户明确要求丢弃时**：先列出将永久消失的东西（分支名、提交列表、worktree 路径），等用户**打出 `discard` 这个词**再动手（"删了吧"不算）。然后切到主仓库根目录，走第 7 步清理，再 `git branch -D <功能分支>`。

### 第 7 步：清理工作区

**只对"选项 1"和"已确认的丢弃"执行**；选项 2、3 永远保留 worktree。清理必须从 worktree 之外执行，用的是第 3 步那三个变量。

- `$gitDir -eq $gitCommon`：普通仓库，没有 worktree，结束。
- `$worktree` 在 `.worktrees\` 或 `worktrees\` 之下：是 `using-git-worktrees` 建的，归我们清。

```powershell
git worktree remove $worktree
git worktree prune                # 自愈：清掉残留登记
```

- **删除被拒**（提示 `contains modified or untracked files`）：说明那里有只存在于该 worktree 的文件（未提交的计划、笔记、草稿）。**绝不自行 `--force`**：先 `git -C $worktree status --porcelain -uall` 把清单摆给用户，再问 ①先提交到 `<分支>` 再清理 ②移到主仓库根目录 ③删除（不可恢复）；照选执行后删除。
- **其它位置**：该工作区属于宿主环境，**原地不动**；不确定归属就不要清。

| 选项 | 合并 | 推送 | 保留 worktree | 删分支 |
|---|---|---|---|---|
| 1 本地合并 | 是 | — | — | 是 |
| 2 建 PR | — | 是 | 是 | — |
| 3 原样保留 | — | — | 是 | — |
| 丢弃（仅明确请求） | — | — | — | 是（强制） |

## 反模式（会怎么错）

| 借口 | 现实 |
|---|---|
| 「刚才测试还是绿的」 | 在**即将集成的这棵树**上再跑一遍；绿只证明它跑过的那棵树 |
| 「他显然是想合并」 | 集成方式是用户的决定，给出菜单然后等 |
| 「顺手提供个丢弃选项吧」 | 菜单就那几项，只有用户明说才走丢弃 |
| 「PR 都建了，worktree 就是垃圾了」 | 评审意见在 worktree 里改，工作真正落地前它留着 |
| 「那个 worktree 看着也过期了，一起清了吧」 | 只清 `.worktrees\` / `worktrees\` 下的，其它属于宿主 |
| 「删除被拒，`--force` 只是把清理做完」 | 被拒意味着有文件只存在于那里，`--force` 会永久销毁 |
| 「合并后测试挂大概是偶发」 | 合并结果失败就全停，分支和 worktree 原地不动 |
| 「基线分支显然是 main」 | 确认分叉点或直接问；合错分支撤销代价高 |

## 完成判据

- 测试在**即将集成的那棵树**上跑过，结果明确（通过项数 / 失败项数）；无测试套件时给出等价证据。
- diff 逐块看过且每个改动都能说清为何在此；临时调试代码、死代码、残留临时文件已清除；无意中的改动已拆出；文档已同步或有"无需变更"的明确结论。
- 交付形态由用户选定，结果与选项一致：选项 1 → 合并结果全绿、分支已删；选项 2 → 推送成功、PR URL 已回报、worktree 保留；选项 3 → 分支与 worktree 均已报告。
- 该清理时 `git worktree list` 里不再有该路径、目录已消失；不该清理时它完好无损。
- 非 git 工作区 → 退化清单（见下）逐条落实。

## 与其它技能的关系

`using-git-worktrees` 管**开头**（开隔离区、跑干净基线），本技能管**结尾**（把工作交付出去并回收那个工作区）；它建的 worktree 正是第 7 步有权清理的那一类。交付前先自己看清 diff（第 2 步），再交给 `requesting-code-review`——它明确要求"合并回主线之前"必须评审。收尾期间每一条"完成"声明都受 `verification-before-completion` 约束：证据先于断言。执行计划收尾时对照 `writing-plans` 的计划逐条打勾。

## 本机适配注意

- 宿主是 DeepSeek Harness 桌面端（Electron，Windows）。**工作目录通常不是 git 仓库**：git 部分整体退化，但**门禁一条不减**，换成"交付前检查清单"：
  - **产物齐全**：用 `glob` 列出、用 `read` 逐个打开确认内容，不是凭"我刚写过"；要交付的用 `present` 报出去。
  - **无残留临时文件**：`glob`/`grep` 扫 `*.tmp`、`*.bak`、`scratch\`、调试脚本与日志；该删的删，该留的说明用途。
  - **可复现**：换目录或重跑能否得到同样结果；依赖、路径、参数有没有写死在临时位置上。
  - **文档同步**：说明文件、README、示例与实际产物一致。
  - **说清退化代价**：没有分支可合、没有 diff 可看、没有 worktree 可清；交付物就是工作区里的最终文件，废弃产物靠人工删——正因为没有 `git checkout` 兜底，上面的清点才更要紧。
- 是 git 仓库时用 PowerShell 语法：`git status` / `git diff` / `git log` / `git merge` / `git branch -d`；路径含中文（如 `G:\家庭网络\...`）要加引号，`git -C "<路径>"` 比 `Set-Location` 稳。
- `pwsh` 在本机有已知故障：返回 `0xC0000142`、零 stdout。**不要反复重试同一条命令**，改用 `read`/`write`/`edit`/`glob`/`grep` 继续（它们不受影响）；确需执行程序再请用户放行。沙箱明确拒绝是另一种形态，会打印 `[sandbox: file access denied ...]`，那是策略拒绝，不是命令失败，也不要换写法绕。
- `workspace-write` 下只有会话工作区可写：worktree 若在工作区之外，创建与清理都可能被拒——按"原地退化"处理，并在报告里写明。
- 需要拍板的地方（交付形态、基线分支、worktree 里有未提交文件怎么办）用 `ask_user_question`；多步收尾用 `todo_write` 记进度；分支检查可以交给 `subagent`，但结论要自己复核。
