# 写技能：给不知情的智能体留判据

读技能的是**不知情的智能体**：它没有你的上下文，不知道你踩过什么坑，也不会来问。所以「要小心」「尽量」等于没写——它无法判断自己是否照做。可执行的只有三样：**可检验的判据**、**反面案例**、**门禁**。

## 何时用 / 何时不用

**用**：从零构思技能的结构与判据；把一次踩坑沉淀成可复用技能；移植上游技能（换成本机工具词汇与判据）；技能存在却没被加载，或加载了但行为没变。

**不用**：跑评测、建基准、批量优化描述 → 交给 `skill-creator`；项目约定写进约定文件；能用校验脚本强制的机械约束就写成脚本，技能只写判断题。

## 核心原则

1. **写判据，不写态度。** 可判定的是「跑什么 → 看什么输出 → 什么算过」；不可判定的一律改写或删除。
2. **每条门禁配反面案例。** 规则会被合理化绕过，要逐个堵死：不许留着当参考、「删就是删」。
3. **描述决定触发。** 目录里只有摘要；描述写不清，技能永远不会被加载，正文再对也没用。
4. **技能也要被测试。** 没看过不知情智能体在**没有**该技能时怎么失败，就不知道该防什么。
5. **体裁要匹配失败类型**，用错会反效果：

| 见过的失败 | 该用的体裁 | 会反效果的体裁 |
|---|---|---|
| 明知规则，压力下仍违反 | 禁令＋借口对照表 | 「尽量」这类软措辞 |
| 照做了但输出形状不对 | 正面配方：写清输出由哪几部分组成 | 一串「不要……」 |
| 老漏掉某个必备元素 | 模板里的必填槽位 | 模板旁的散文提醒 |
| 行为应视条件而定 | 条件式，绑在可观察的判据上 | 无条件规则＋例外说明 |

也别写「除非……否则不要 X」：让步从句把定型的措辞变回可谈判的；例外单独写成条件式。

## 流程

按 RED → GREEN → REFACTOR 走，顺序不可换。

**1. RED：先看它怎么失败。** 不加技能做同一件事：自己换个说法试，或派 `subagent` 用不知情提示词试（只给用户会说的原话，不暗示期望答案）。逐字记下它选了哪条路、用了什么借口。
判据：至少拿到一条「具体失败行为＋原话借口」。写不出，说明这事还不需要技能，停。

**2. GREEN：写最小技能。** 只针对上一步记下的失败，不为假想情况加内容。
- 路径 `skills/<name>/SKILL.md`；frontmatter 只写 `name`（与目录同名、kebab-case、只用字母数字和连字符）与 `description`（可加 `whenToUse`）；不写本 harness 不消费的键。
- 描述三段：① 做什么（一句话）；② 何时用（具体症状）；③ 用户会怎么开口（触发词）。**不要把流程概括进描述**——上游实测：描述带流程时，智能体照描述做而不再读正文。
判据：把描述单独给一个不知情智能体看，它能说出「什么情况该加载它」。

**3. REFACTOR：堵新借口。** 把测试中新冒出的借口补成明文禁令或对照表里的一行，再跑同一场景，直到不再有新借口。

**4. 验证：用真实提问试。** ① 换个说法问同一件事，看它会不会 `skill(name="<技能名>")` 加载；② 派 `subagent`，提示词只给用户原话，看它是否自行加载并按判据行动。看**行为**，不看它背没背下来。
判据：描述命中 + 行为改变，两条都要有。缺前者改描述，缺后者说明判据不够可判定。

## 门禁（硬性）

- **没有失败基线的技能不写。** 没先看到失败就动笔，防的是你猜出来的错。写完才发现没基线 → 删掉重来，不许留着「当参考」。
- **没验证过不算完成。** 「描述很明显」「正文很清楚」不是证据：清楚是对你，不是对它。
- **一次只测一个技能。** 批量写完再一起测，等于没测。
- **只落真源，不许只落某个目标**（见「本机适配注意」）。
- **技能不是叙事。** 「我当时怎么解决的」不可复用，要写成判据与步骤。

## 反模式（会怎么错）

| 想法 | 现实 |
|---|---|
| 「这技能显然很清楚，不用测」 | 清楚是对你。没看过失败基线，就不知道防得对不对。 |
| 「描述里把流程也写上，更好懂」 | 智能体照描述做，正文被跳过。只写做什么／何时用／触发词。 |
| 「加句『除非……否则』更周全」 | 让步从句重新打开谈判，实测从稳定变噪声。 |
| 「用『尽量』『注意』提醒一下」 | 无法判定是否照做，等于没写。 |
| 「纯参考资料不用测」 | 参考资料也会缺页、找不到。要测「取得到吗、用得对吗」。 |
| 「先写进某个工具的 skills 目录」 | 那是分发产物，会与真源漂移。先落真源。 |
| 「顺手把另外两个也写了」 | 批量＝没测。 |

## 完成判据

- frontmatter 只有 `name`／`description`（可加 `whenToUse`），`name` 与目录同名且 kebab-case；
- 描述含「做什么／何时用／触发词」，且**不含**流程概括；
- 每条叮嘱都已改成「跑什么 → 看什么 → 什么算过」，或已删除；
- 有一条来自真实试跑（或不知情 `subagent`）的失败基线记录；
- 验证证据两条齐全：描述命中 + 行为改变；
- 文件落在真源 `D:\Tools\skillshare\skills\<name>\SKILL.md` 并已分发（或已请用户分发）；
- 与既有技能无职责重叠，尤其没和 `skill-creator` 抢同一件事。

## 与其它技能的关系

- **与 `skill-creator` 分工**：从零构思结构与判据 → 本技能；跑评测、建基准、多轮优化描述 → `skill-creator`。
- 技能内容是一套实现流程时，步骤—判据的体例可参考 `writing-plans`；纪律类措辞可参考 `test-driven-development`、`verification-before-completion`。

## 本机适配注意

- **本仓库的技能由插件提供**：插件扫描包内 `skills/` 并注册进 harness，路径固定为 `skills/<name>/SKILL.md`，目录名必须等于 frontmatter 的 `name`。插件自带的极简解析器只认顶层 `key: value`（支持 CRLF/BOM），缩进嵌套块会被跳过——不要写嵌套 YAML。
- **真源与分发**：本机技能真源是 skillshare 的 `D:\Tools\skillshare\skills`，分发到 7 个目标。**新技能必须落到真源再分发**；只写进某个目标的 `skills/` 会与真源漂移，下次同步被覆盖。分发命令见 `skillshare` 技能。
- **沙箱**：文件策略常为 `workspace-write`，只有会话工作区可写。真源在工作区外时 `write` 会被拒绝（`[sandbox: file access denied ...]`）——**不要换路径硬写**，把完整 SKILL.md 留在会话里，并请用户执行「写入真源 + 分发」。
- **未移植的上游附属文件**：`anthropic-best-practices.md`、`testing-skills-with-subagents.md`、`persuasion-principles.md`、`examples/`、`graphviz-conventions.dot`、`render-graphs.js`。需要更多细节时用 `web_fetch` 取上游原文，别凭记忆编。流程图不移植：用 Markdown 表格写「条件 → 走哪条路」。
- **工具名**只用本机词汇（`read`／`write`／`edit`／`glob`／`grep`／`pwsh`／`subagent`／`skill`／`todo_write` 等）；上游其它 harness 的工具名要逐个替换。`pwsh` 在 `workspace-write` 下可能返回 `0xC0000142` 零输出，判据不要只依赖「跑一条命令」。
