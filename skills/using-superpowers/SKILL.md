# 用技能：入口与加载顺序

本技能只解决一件事：**动手之前，先确认该用哪个技能**。它自己不干活，只规定判断与加载的纪律。
技能是「这件事该怎么做」的说明书；跳过加载直接凭直觉作答，等于把过去踩过的坑重踩一遍。

## 何时用 / 何时不用

用：
- 任何一次对话或任务的**第一步**，包括看起来很简单的问题；
- 用户直接点名技能（「用 brainstorming 帮我理一下」）——直接 `skill(name="brainstorming")`；
- 准备进入计划模式，或准备说出「做完了」之前。

不用：
- **你是被派来执行单一具体任务的子智能体**（由 `subagent` / `subagent_fork` 派出）。
  此时按派发提示词指定的技能执行，不必再走一遍本技能；
- 场景与技能主题完全无关，且已确认长期记忆里也没有对应的既有技能。

## 核心原则

1. **1% 原则**：只要有哪怕 1% 的可能某个技能适用于当前这件事，就必须先加载它。
   这不是「看情况」——技能适用就必须用，没有可选项。加载后发现不适用，可以不照着做，
   但**加载这一步不能省**：「我觉得用不上」几乎总是合理化。
2. **加载先于一切**：在**任何**回复或动作之前加载，包括反问澄清、翻代码库、看文件、查状态。
   问题也是任务，澄清也是动作。
3. **先查记忆与既有技能，再套方法论**：本机除本技能包外，还有一批 skillshare 分发的本地
   运维/文档类技能，以及本仓库的长期记忆（Hindsight 知识页）。判断「用什么」时先检索这两处；
   若本地技能已精确覆盖（例如某个具体服务的排障），就走它——不要为了走流程，把一个小任务
   拖进重型方法论。
4. **用户指令 > 技能 > 默认行为**：用户直接说的话（含项目约定文件）优先于技能；
   只有用户明确说「不用走那套流程」时，才可跳过技能规定的工作流。
5. **先宣布再执行**：加载后声明「正在用 <技能名> 做 <目的>」，然后严格照它执行；
   它若有检查清单，用 `todo_write` 一次提交完整清单，逐项闭环。

### 加载顺序（多个技能都适用时）

后面的不可越过前面的：
1. **用户点名或直接要求的技能**；
2. **本地既有技能**（skillshare 分发的运维/文档类）——前提是精确命中当前场景；
3. **过程类技能**：`brainstorming`、`systematic-debugging` 等，它们决定「怎么走」。
   「我们做个 X」→ 先 `brainstorming`；「修个 bug」→ 先 `systematic-debugging`；
4. **实现类技能**：`test-driven-development`、`writing-plans`、`subagent-driven-development` 等，
   在过程技能定好方向之后再加载。

同名冲突：本机**本地技能优先**。本插件 rank 是官方 bundled 档（600），不抢用户/项目技能的位置，
所以 `skill(name=...)` 拿到的是本地那一份——这是刻意设计，不是故障，也不必「修」它。

## 流程

1. **看任务**：用一句话写下这件事要产出什么。
2. **查已有**：检索本仓库长期记忆与本地技能清单。（技能目录随会话注入，但目录里**只有摘要**。）
3. **定候选**：按上面的加载顺序列出候选技能。
4. **加载**：对每个候选调用 `skill(name="<技能名>")`，逐个加载；加载后读全文。
5. **宣布**：说明正在用哪个技能、为了什么目的。
6. **照做**：若有清单，用 `todo_write` 建任务列表，逐项执行、逐项闭环。
7. **收尾**：按 `verification-before-completion` 的思路核对判据，再给结论。

## 反模式（会怎么错）

下列念头一出现就**停**——它们都是合理化：

| 念头 | 事实 |
|---|---|
| 「这只是个简单问题」 | 问题也是任务，先查技能。 |
| 「我得先了解上下文」 | 技能检查在澄清提问**之前**。 |
| 「先翻翻代码库 / 先收集信息」 | 技能会告诉你该**怎么**翻、**怎么**收集。 |
| 「看个文件很快的」 | 文件没有对话上下文。先查技能。 |
| 「这不用上正式流程」 | 存在技能就用。 |
| 「我记得这个技能」 | 技能会演进，读当前版本。 |
| 「这不算一个任务」 | 有动作就是任务，先查技能。 |
| 「用技能太重了」 | 简单的事会变复杂，正因如此才要用。 |
| 「我先做这一件小事」 | 在**做任何事之前**先查。 |
| 「这样感觉很有效率」 | 无序的行动才浪费时间，技能就是防这个。 |
| 「我知道那是什么意思」 | 懂概念 ≠ 用过技能，加载它。 |

另一类错误：把本地运维小任务（改个配置、看段日志）硬套重型流程，产出一堆没人要的计划文档。
这同样违反核心原则第 3 条。

## 完成判据

- 在**第一句实质回复之前**，已完成「查记忆/本地技能 → 列候选 → 加载」；
- 每个判定适用的技能，都有一次对应的 `skill` 调用（能说出技能名），而不是「我记得」；
- 有一句明确的「正在用 <技能名> 做 <目的>」；
- 技能要求的检查清单，与 `todo_write` 提交的清单项一一对应；
- 收尾前对照技能自身的完成判据逐条核对，而不是凭感觉宣布完成。

## 与其它技能的关系

- 本技能是入口，**每次任务先过一遍**；
- 设计规划链：`brainstorming` → `writing-plans` → `executing-plans`；
- 排障链：`systematic-debugging` → `test-driven-development` → `verification-before-completion`；
- 协作交付：`subagent-driven-development`、`dispatching-parallel-agents`、
  `requesting-code-review` / `receiving-code-review`、`finishing-a-development-branch`、`using-git-worktrees`；
- 元技能：`writing-skills` 写技能、`diagnosing-superpowers` 排查技能包本身；
- 本机另有 skillshare 分发的本地运维/文档技能，**同名时以它们为准**。

## 本机适配注意

- 上游是围绕另一套 harness 的工具词汇写的：文中出现的工具名一律按
  `references/dsh-tools.md` 的对照表翻译成 `read` / `write` / `edit` / `glob` / `grep` /
  `pwsh` / `subagent` 等再执行，不要照着叫；本机的技能加载工具就叫 `skill`。
- 技能目录随会话注入，只有名字与摘要；**正文必须先 `skill` 加载才可见**，不要凭摘要动手。
- 不要因为 `glob` 没列出某个技能目录就断定技能不存在：Windows 下技能目录常是符号链接，
  `**` 不跟随，要用 `read` 直接穿透确认。
- **进入计划模式或提交计划之前**，若尚未头脑风暴，先加载 `brainstorming`。
- 文件策略常为 `workspace-write`，且 `pwsh` 可能返回 `0xC0000142` 零输出。这不影响本技能：
  继续用 `skill` / `todo_write` / `read` / `grep` 即可，不要反复重试同一条命令。
