# 请求代码评审（requesting-code-review）

改动做完之后，派一个独立上下文的评审者审一遍，把问题挡在它滚成雪球之前。一份值得做的评审请求不是一句「帮我看看」，而是四样东西：**说清改动意图与范围**、**附上可核对的证据**、**明确希望评审者回答的问题**、**把范围切到一个可独立理解的变化**。上游的原则是：**早点审，经常审。**

## 何时用 / 何时不用

**必须评审**：`subagent-driven-development` 里每个任务完成后；主要功能完成后；合并到主干前。

**可选但值得**：卡住时（换个视角）；重构前（先建立基线）；修完复杂 bug 后。

**不该用一次评审解决的**：改动本身还没成形（先把它做完，或明确说清哪些是半成品）；一次混了好几个互不相关的变化（先切分，见流程第 1 步）。

## 核心原则

1. **评审者必须独立——不能是改动作者本人。** 作者脑子里装着「我为什么这么写」，看不见自己没写出来的假设。本机的做法是用 `subagent` 起一个**全新上下文**的评审者：它看不到你的会话、你的推理、你的试错过程。这既是它的价值（只看产物本身判断），也是你的义务（**你看得懂的地方它未必看得懂，材料必须给全**）。
   - 不要用 `subagent_fork` 做这次评审：fork 会继承本会话上下文，评审者等于「看见」了你的思路，独立性就没了。
   - 也不要用「自己 inline 看一遍 diff」代替评审：作者不是评审者；而且那一大坨 diff 会把你要用来继续推进工作的上下文窗口烧掉——diff 和评估应该待在评审者的上下文里，回来的只有结论。
2. **意图与范围先写清楚**：这次改动要达成什么、依据是哪份计划/需求、边界在哪里（顺手改了哪些、故意没改哪些）。
3. **证据要可核对**：diff、跑过的命令与原始输出、`路径:行号`。没有证据的判断不算数。
4. **一次评审只覆盖一个可独立理解的变化。** 范围大就先切分——评审者能一次抓住的是一件事，不是一坨。
5. **把问题问明确**，并给出期望的输出形状。泛泛提问只会换回泛泛的评论。

## 流程

1. **定范围。** 用一句话说出「这次改了什么、为什么」。若这一坨里混了新功能、顺手重构和格式化，先拆成多次评审；拆不开就明确写出「哪些不在本次范围」。
   判据：范围能用一句话说完，且它能被独立评审（评审者可以否掉这一坨而不牵扯别的）。
2. **准备可核对的证据。**
   - **是 git 仓库**（本机不一定是，先确认：用 `pwsh` 跑 `git rev-parse --is-inside-work-tree`，能打印 `true` 才算）：用 `pwsh` 取 diff——
     ```powershell
     git diff --stat HEAD~1..HEAD
     git diff HEAD~1..HEAD
     ```
     有明确起点时用 `git merge-base origin/main HEAD` 或具体 SHA 代替 `HEAD~1`。
   - **不是 git 仓库**（本机常态）：直接**把证据交给评审者**——用 `read` 读出改动前后涉及的文件内容与新增文件全文，连同跑过的命令和原始输出、`路径:行号` 一起写进评审请求；也可以在工作区内给出文件路径，让评审者自己 `read`（它和你共享工作区）。
   判据：评审者不需要反问你，就能看到「改之前是什么、改之后是什么」。
3. **起独立评审者（`subagent`）。** prompt 必须自包含，至少含这七块：
   - **实现了什么**：一段话。
   - **需求/计划**：计划文件路径或任务原文（这是判断「是否偏离计划」的依据）。
   - **改动范围与证据**：第 2 步产出的 diff 或文件内容/全文。
   - **只读约束**：评审是只读的，不要改动工作区文件、工作树、索引或 HEAD。
   - **不许再派 subagent**：太大就自己分几遍看，并在报告里说明分了几遍——评审座位已经占满，再派的复核不计分。
   - **判据尺度**：需求文档没写到的行为，按「一个正常使用这个软件的人会期待什么」来判断，沉默不等于许可；开工前先列出「我考虑过但搁置不判的行为」清单（每行一条加理由），交给发起方裁决，不许悄悄丢掉。
   - **输出格式**：优点 / 问题（**Critical 必修**、**Important 应先修**、**Minor 可选**，每条给 `路径:行号` + 错在哪 + 为什么要紧 + 怎么修）/ 建议 / 结论（**可以合并｜不可以｜修完可以**，附 1–2 句技术理由）。要求它按真实严重度分级，别把吹毛求疵标成 Critical，也别在没读过的代码上给意见。
   判据：把这段 prompt 原样交给一个不认识你的人，他就能开工。
4. **派发并等结果。** 用通知或 `list_agents` 拿结果，不要空转轮询，也别在等待期间去改评审涉及的文件。
5. **处置反馈。** Critical 立即修；Important 修完再往下推进；Minor 记下来以后说。评审者判错时**带着技术理由反驳**，贴出代码或运行结果证明它成立，或请它澄清——不要为了省事照单全收，也不要硬顶。这一半的动作归 `receiving-code-review`。
6. **反馈量大到看不清主次时**，说明第 1 步的范围没切对：回到第 1 步切分，而不是硬着头皮逐条应付。

## 反模式

- **「改动很简单，跳过评审吧。」** 门禁里点名的第一条。
- **没有意图、没有范围、没有证据、没有问题的「帮我看看」。** 评审者只能回一堆泛泛而谈。
- **把整个会话历史倒给评审者**（「它得看完我的会话才懂」）。要的是精心裁剪的材料，让它盯产物，而不是盯你的心路历程。
- **作者自审冒充评审**，或拿 `subagent_fork` 当独立评审。
- **一次审一大坨**：几个不相关的变化塞进同一次评审，问题互相淹没，反馈落不到具体位置。
- **无证据的完成宣告**：说「我测过了」「已经修了」，却不给命令和输出。
- **忽略 Critical、带着未修的 Important 继续往下做**；与有效的技术反馈争辩。
- **让评审者再去派 subagent 复核**：重复占座，结论不计。

## 完成判据

- 评审由一个**独立上下文**完成：`subagent` 起的、不是作者本人、不是 fork 本会话。
- 评审请求里四样齐全：改动意图、范围、可核对证据（diff，或改动前后文件内容/新增文件全文 + 命令输出 + `路径:行号`）、希望评审者回答的问题与输出格式。
- 评审者只看材料即可开工，没有回头追问你的会话上下文。
- 报告给出明确结论（可以合并 / 不可以 / 修完可以），问题按 Critical/Important/Minor 分级且带 `路径:行号`。
- 每个 Critical 已修或已带理由驳回；Important 在继续下一步之前已修，或已有带理由的处置决定。
- 本次评审只覆盖一个可独立理解的变化。

## 与其它技能的关系

- 配对技能是 **`receiving-code-review`**（收的一方）：本技能管「怎么发起一次值得做的评审」，它管「拿到反馈后怎么处置、怎么反驳、怎么闭环」。两者成对使用。
- 上游链路：`subagent-driven-development` 的每个任务收尾 → **本技能** → `receiving-code-review` → 修完再验。
- 评审所需的「需求/计划」来自 `writing-plans` 产出的计划文件；写计划时把评审聚焦点写进去，评审时把它交给评审者。

## 本机适配注意

- 宿主是 DeepSeek Harness 桌面端（Windows）。文件策略常为 `workspace-write`：只有会话工作区可写，工作区外路径会被沙箱拒绝，报 `[sandbox: file access denied ...]`。评审材料请限定在工作区内。
- **工作目录通常不是 git 仓库**，所以第 2 步的 diff 获取写成条件式：有 git 才取 `git diff`；没有就直接给改动前后的文件内容与新增文件全文——**退化后的判据不变**（评审者能看清改前改后），而不是「因为没 git 就不审了」。
- `pwsh` 有已知故障：可能返回 `0xC0000142` 且零 stdout（与沙箱拒绝是两种形态）。遇到时不要重复重试同一条命令，改用 `read`/`grep`/`glob` 继续取证；确需执行程序再请用户放行。
- 上游的评审者 prompt 模板是同目录的 `code-reviewer.md`，本机**不移植该附属文件**，其要点（只读、不再派 subagent、判据尺度、输出格式、分级）已并入流程第 3 步，直接照它写 prompt 即可。
