# 把想法澄清成设计（brainstorming）

这个技能解决一个问题：**在没有共同理解之前就动手写代码，最后交付的不是对方要的东西**。它的产出不是代码，而是一份对方能看懂、能纠正的设计理解。所谓「简单到不需要设计」，几乎总是判断失误——本技能的门禁是「获批」，不是「设计有多长」。

## 何时用 / 何时不用

**用**：新功能、新组件、新子系统、新项目；改动会打散模块边界或影响别人依赖的接口；用户说「我想做个 X」「先规划一下」「这样可行吗」。

**不用（直接跳过本技能）**：本机大量任务是运维／排障，这类工作不该走设计流程：

- 目标是「让现状恢复预期」而不是「增加新行为」——服务挂了、DNS 解析错了、容器起不来、采集返回 0 条、证书过期。判据：**你现在想要的是修复，不是新的设计选择**。
- 已有明确的复现步骤和验收标准，缺的只是定位与执行。
- 用户已给出完整方案（「照这个做」），你只需执行。
- 纯信息查询、纯读取、纯解释。

判据速记：**如果这件事做完之后，系统对外行为与之前完全相同，那就是排障，不是设计。** 拿不准时先问一句「你要的是修好它，还是要改它的做法？」——一句话的成本远低于一次跑偏的设计。

## 核心原则

1. **先分级，再提问，并说出分级。** 在第一个问题之前就宣布「这看起来是 bounded，我会在这里给个简短设计而不是写 spec」，让对方能推翻你的判断。
2. **一次只问一个问题。** 每条消息只放一个问题；一个话题需要深挖就拆成多轮。优先给多选题，开放式也可以。不要一口气甩出七八个问题审讯用户。
3. **区分「他说的」和「你猜的」。** 复述理解时把两者分开写，邀请纠正；对方纠正后要吸收，再当作设计简报。
4. **路径只能升不能降。** 中途发现隐藏复杂度就停下来说明并升级路径；没有任何情况可以在中途降级。两可之间取更重的路径。
5. **门禁是「获批」，不是「设计写完了」。** 呈现设计之后必须停下，等到明确的同意。

## 流程

### 第 0 步：分级（三选一）

- **Spike（探针）**：可行性问题（「能不能……」「可不可能……」「快速粗糙也行」），产出是**答案，不是要留下的代码**。用 2–3 句话说明你要验证的问题和打算怎么试，得到点头后，以正确性允许的最低成本去试。不写设计文档，不写 spec。结论以「建议」形式汇报，任何搭出来的东西都要标注为一次性弃用。
- **Bounded（有界改动）**：对**本仓库里已经存在的流程**做范围明确的修改——加个开关、加个小接口、单文件修复。判断依据是「你要改的那段流程已经在这里可以读到」，你对这类应用的熟悉程度不算数。问清楚真正关键的问题，在**会话里**给出简短设计（几句话到几段话），然后**停下**。对方说「可以」之后才实现。
- **Architectural（架构级）**：新项目、新子系统、会重组组件关系或改动他人依赖的接口。走完整流程：提问 → 备选方案 → 分节设计 → 写 spec → 交给 `writing-plans`。

### 第 1 步：建立共同理解

- 先看现状再开口：用 `read`／`glob`／`grep` 检查相关文件、文档、近期改动（本机通常不是 git 仓库，那就直接读代码与目录结构）。
- **先判规模**：如果请求里包含多个互相独立的子系统（例如「做一个带聊天、文件存储、计费和统计的平台」），立刻指出需要先拆分，别浪费问题去打磨一个该被拆开的项目。拆成子项目后，只对第一个子项目走正常设计流程，每个子项目各有一轮 spec → plan → 实现。
- 询问时聚焦三件事：**目的、约束、成功判据**。知道这是哪一类应用，并不等于知道对方为什么要它。
- 如果请求本身已经给足了目的和约束，就直接复述这份理解，不要重复提问。
- 把理解写成一段简短简报，分开「你说的」和「我假设的」，请对方纠正后再当作设计简报。

**判据**：对方明确确认或纠正过这份简报；此后所有功能与技术选择都要拿它来对。

### 第 2 步（Bounded）：提问 → 会话内简短设计 → 获批

设计需覆盖：采用的做法、会碰哪些文件、怎么验证。写清之后立刻停下等明确的「可以」。把设计和「我开始写了」放在同一条消息里，等于跳过门禁。

### 第 3 步（Architectural）：提问 → 备选方案 → 分节设计 → spec

- **提问**：一次一个，理解目的、约束、成功判据。
- **2–3 个备选方案**：带权衡，先说推荐的那个并说明理由；对每个方案狠用 YAGNI，删掉不必要的功能。
- **分节呈现设计**：每节按复杂度伸缩——直白处几句话，微妙处可到 200–300 字；每节问一句「到这里对吗」，覆盖架构、组件、数据流、错误处理、测试。
- **为隔离而设计**：把系统拆成各自目的单一、通过明确接口通信、可独立理解和测试的单元。对每个单元都要能回答：它做什么、怎么用、依赖什么。别人不读内部实现能否明白它做什么？改内部会不会破坏使用方？不能，就是边界没划好。
- **在既有代码里工作**：先看现有结构与模式，跟着它走。与本次目标相关的既有问题（文件过大、边界不清、职责纠缠）作为定向改进纳入设计；不相关的重构不要顺手做。

### 第 4 步：写 spec 并自审（仅 Architectural）

- 写到 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`（用户另有指定位置则以用户为准）。本机不是 git 仓库时不必提交，但必须在会话里给出该路径并请对方查看。
- **自审**：① 占位符扫描——还有 TBD／TODO／含糊需求吗？② 内部一致性——各节互相矛盾吗，架构与功能描述对得上吗？③ 范围——是否聚焦到能出一个实现计划，还是需要再拆？④ 歧义——有没有哪条需求能被两种方式理解？有就选一种并写明。发现问题**就地改掉**，不必再来一轮。
- **用户评审门禁**：自审通过后请对方评审这份 spec，并等待回复。对方要求修改就改，然后重跑自审。只有对方认可才继续。

### 第 5 步：交接到实现

获批后，**只**调用 `writing-plans` 技能来编制实现计划。不要调用任何其它实现类技能。Spike 到此结束于一份建议；Bounded 获批后走正常开发流程（若本机有测试运行器则照常 TDD，没有就用可复现的手工验证步骤替代）；Architectural 到此结束于 `writing-plans`。

## 门禁（硬性）

在采取任何实现动作之前——包括调用实现类技能、写产品代码、搭脚手架、安装产品依赖、创建外部项目——必须先完成所选路径的前置条件：

- **Spike**：对方认可要验证的问题和探针方案。
- **Bounded**：对方认可会话里的简短设计。
- **Architectural**：对方评审并认可书面 spec，之后再评审书面实现计划并选择执行方式。**会话中的设计认可只授权写 spec；spec 获批只授权调用 `writing-plans`。**

**获批的形态**：对方**明确说可以**（「可以／就这样／开做吧」），或**明确确认了方案**。沉默、没反对、只说「嗯」「继续」都不算。一次回复只批准**当时呈现的那个阶段**——认可了想法或功能范围，不等于批准了尚不存在的产物。从最早的未完成阶段继续，不要把一次批准放大成跳过剩余阶段的通行证。在这些前置条件完成期间，只读的项目探查是允许的。

## 反模式（会怎么错）

| 想法 | 现实 |
|---|---|
| 「这太简单了，不用设计」 | 按所选路径走：有界改动给简短会话设计，架构级改动给书面 spec 与计划交接。 |
| 「我把它算作 bounded 就能跳过 spec」 | 为了省事去找标签，这个念头本身就是疑虑——取更重的路径。 |
| 「设计很明显，我边写边等他们看」 | 门禁是获批，不是设计的长度。呈现，然后停，等到听见「可以」。 |
| 「我熟悉这类应用，所以是 bounded」 | bounded 衡量的是仓库，不是你的熟悉度。新项目没有既有流程，它是架构级。 |
| 「探针跑通了，代码就留着吧」 | 探针的产出是答案。留下代码是一个新请求，要重新分级。 |
| 「它变大了，但我快做完了，不用重新分级」 | 隐藏复杂度会使路径中途升级。停下来说明。 |
| 「他们批准了探针，后续改动也就批了」 | 每个任务各有一次分级、各有一次批准。 |
| 一次抛出七八个问题「确保问全」 | 审讯用户会耗尽对方的注意力。一次一个，只问真正改变设计的那些。 |

## 完成判据

- 路径已明确说出，且与任务实际重量相符（拿不准时取了更重的一条）。
- 关键问题已问清：目的、约束、成功判据都有答案，或已被对方确认「不用问」。
- 设计理解以**书面文字**留在会话里（架构级另有一份 spec 文件路径）；其中「你说的」与「我假设的」已分开。
- 存在一条可指认的**明确同意**记录，覆盖当前阶段。
- 架构级：spec 已写、已自审、已被对方评审认可。
- 下一步已指明：加载 `writing-plans`（架构级），或进入正常开发流程（bounded）。

## 与其它技能的关系

`brainstorming` → `writing-plans` → `subagent-driven-development`（或本机等价的执行方式）。本技能是这条链的第一环；架构级路径的终点**只有** `writing-plans`，不要在这里直接接实现类技能。若本机装有风格类技能，写 spec 时可参考其写作规范。

## 本机适配注意

- **本版没有可视化伴随。** 上游带一个基于浏览器的可视化伴随（brainstorm server：零依赖 node 服务，用浏览器页展示 mockup、图表、选项对比）。**本机不移植它**：本技能全程用**纯文本对话**完成设计澄清，**不启动任何本地服务、不开浏览器标签页、不读写可视化配置**。遇到「看图比看字更清楚」的场景（布局、线框图、结构图），退化为用 Markdown 表格、ASCII 草图或分点描述在会话里表达，并说明这是本机形态。
- 上游附属文件 `visual-companion.md`、`spec-document-reviewer-prompt.md` 与 `scripts/` 均未移植；spec 评审就是上面的自审 + 用户评审门禁。
- 只读探查用 `read`／`glob`／`grep`，不要为看代码去执行命令。本机 `pwsh` 在 workspace-write 策略下存在已知故障（返回 `0xC0000142`、零 stdout），确需执行程序时不要反复重试同一条命令。
- 写文件用 `write`／`edit`：只有会话工作区可写，工作区外路径会被沙箱拒绝（打印 `[sandbox: file access denied ...]`）。spec 落在 `docs/superpowers/specs/` 下属于工作区内，可行；若工作区不可写，就退化为把完整 spec 正文留在会话里，并明确告知对方这一退化。
- 工作目录通常**不是 git 仓库**：需要「提交文档」的那一步退化为「给出文件路径 + 在会话里贴出要点」，不要假装提交过。
- 需要用户做选择时，用 `ask_user_question` 一次问一个关键问题比连续多发消息更省事；但问题本身仍然要节制。
- 提问前若涉及外部事实（库的现状、接口是否还存在），用 `web_search`／`web_fetch` 查证，别凭记忆断言。
